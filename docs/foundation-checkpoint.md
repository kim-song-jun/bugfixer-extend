# Internal foundation checkpoint: project, task, and review

Status: **internal implementation checkpoint draft**, not a user-facing release or approval to import source or implement product code. The user selected [C for the first macOS task experience](first-macos-task-scope.md): archive, manual order, multiple reviews, deletion, and real agent-driven state handling must also work before that experience is accepted. This narrower checkpoint proves the selected foundation, app-owned database, per-project native windows, and dashboard/file/review tabs before the C capabilities are added. The dashboard's detailed arrangement remains a separate A/B/C choice shown in the local `dashboard-layout-decision.html` comparison. The provisional controls below are checkpoint scaffolding, not a substitute for the selected C scope.

## Checkpoint behavior

1. Open or create a project from a local folder. One project has one native Code OSS window. Opening it again focuses that window; opening another project leaves both windows' folder, tabs, and selected task independent. A moved folder keeps the project and task IDs and asks for an explicit rebind. Git/jj detection enables review creation; an ordinary folder still supports projects, tasks, and file editing.
2. The project dashboard opens as a native editor tab. It has a direct **Create task** action, the four selected board states (**Ready**, **In progress**, **Review**, **Done**), and a task detail view. The pending dashboard A/B/C choice will fix their final placement. There are no inert agent, import, or E2E controls in this checkpoint.
3. Create a task with a nonempty title and optional description in the current project's folder binding. The provisional default state is Ready. A person can edit its title/description and move it among the four board states. Review creation does not move the task by itself in this checkpoint. The board updates after the workspace database commits and shows an error without a false state change if the write fails. Task deletion enters the selected C stage once its retention contract is approved.
4. Open a task's file in the same window's ordinary editable Code OSS tab. If two tasks open the same file, the file tab can be reused but task selection changes explicitly; a saved edit is not silently attributed to the other task. Returning to the dashboard restores its selected task and scroll position.
5. **Create review** registers the available Git/jj checkout with Whiteboard, creates a Review document or recovers the same result on an identical-command retry, saves the returned `reviewId`, and opens `api:<reviewId>` in that project's native tab. Repeating the action opens the stored link without creating another review. A separate future pull-request target may return an already existing PR review; the returned ID remains authoritative. A missing/deleted review shows an unavailable link and a repair action, not a silent replacement.

This checkpoint proves local app services with Docker stopped; it does not decide where the selected C agent execution runs. Its precise UI copy, spacing, and compact layout follow [ux-flow.md](ux-flow.md) after the dashboard arrangement is selected. The C stage adds real agent runs against these stable project and folder bindings; no fake run state appears before a real adapter exists.

## Persisted contract in `workspace.db`

| Record | Stable keys and required data | Invariant |
| --- | --- | --- |
| Project | App UUID, display name, creation time | Moving its folder never changes the UUID. |
| Folder/checkout binding | App UUID, owning project UUID, current path, nullable Git/jj identity and root status, current Review `repositoryId` when registered | The project owns its binding. An ordinary folder needs no Review repository ID. Review repository IDs are profile-local and never become project IDs. A rebind records the new path/registration without editing old Review create payloads. |
| Task | App UUID, project UUID, checkout binding UUID, title, optional description, board state, deterministic order and revision | The referenced checkout belongs to the same project. State and order change in one transaction; task/project identity never follows a reused file tab. |
| Review outbox | Stable `commandId`, task UUID, exact immutable create body, pending/complete/failed status, last error, returned `reviewId` when known | Persist before the Review API call. A retry sends the same body and ID; a changed target is a new explicit command. |
| Task-review link | Task UUID, returned `reviewId`, link state, relationship role | The checkpoint can show one primary review per task; the selected C experience must display and choose among multiple links. The same review ID may belong to more than one task, so no global uniqueness assumption on `reviewId`. |
| Project view | Project UUID, app-owned workspace descriptor URI, open-at-quit flag, selected task UUID, dashboard position | Native window ID is ephemeral and never stored as project identity. File/review editor groups restore under this project's workspace URI. |

SQLite foreign keys and main-process ownership enforce the relationships. The main process is the only `workspace.db` writer; renderers call a typed API that checks their bound project/window. Provider and Review tokens, server URLs, and connector secrets do not become task columns. Schema migrations and writes are transactional; a failed migration leaves the prior database usable and reports a repairable error instead of opening an empty board.

The checkpoint can start with stable creation order within a state and append a moved task to the destination state. A state move stores the task revision and ordered positions atomically so two windows cannot overwrite a newer change without a conflict result. User-facing board actions remain keyboard accessible. The selected C experience also needs persisted manual order and recovery after concurrent edits. Drag interaction and the final inspector placement follow the selected dashboard layout; they do not change task identity.

## Review write and recovery sequence

1. Recheck the task's folder binding when review creation starts. If the folder is inside an available Git/jj checkout, send that folder path to the supported Review API; Whiteboard resolves and registers the VCS root, and the returned `repositoryId` is saved on the binding. A project may point to a subfolder rather than the repository root. If the folder is missing or outside supported VCS, keep the task editable but disable only review creation with a specific rebind/registration explanation. Rebinding repeats VCS detection.
2. In one workspace transaction, save an outbox row with a UUID `commandId` and exact Review API create body: `operation:{type:"create",title,target:{kind:"worktree",repositoryId},open:false}`. The task title at this moment is the review title; a later task rename does not rewrite it.
3. Send the saved body through the main-process Review gateway. If the response is lost, restart reconciliation retries the same body and `commandId`; Whiteboard's command receipt returns the same result. On success, save the returned `reviewId`, insert the task link, and mark the outbox complete in one workspace transaction. A permanent error keeps the command and message visible for explicit repair. The two databases do not share a transaction.
4. Resolve the task's project window and open its Review tab there. The global `/:id/open` endpoint cannot select a project window on its own. If the review was deleted, leave the link visible as unavailable until the user repairs it.

The [architecture write contract](architecture.md#review-link-write-contract) is authoritative for Review API identity and idempotency. The [window integration contract](project-window-integration.md) details the single control stream and token-owning gateway required before this flow can run safely in multiple windows.

## Acceptance evidence

- From the **committed** source tree, the imported Review baseline builds and launches; its licenses/notices and source pin remain visible. The product project mode then builds and launches on macOS without Docker running.
- Two project windows show distinct project/task data and restore their own dashboard, active task, file tabs, and review tabs after restart. Two projects bound to one checkout still keep window/tab identity separate. A missing checkout offers rebind without loading another project's files.
- Create/edit/move tasks, restart, and confirm title, description, state, and deterministic order persist. A failed database write leaves the displayed task unchanged. Agent-driven transitions are proved in the C stage, not inferred from this checkpoint.
- Edit and save a real checkout file. Open that file from two tasks and verify the visible task context changes explicitly. The Review source navigator still opens a separate read-only historical workspace.
- Create a task review, simulate a lost API response and restart, then recover one returned `reviewId` and one tab. Opening the same link repeatedly reuses the tab; a deleted review remains a visible broken link. Direct canvas opening after `open:false` loads the review. The app main process retains the only Review control stream and token; project renderers expose neither. External `/:id/open` routes a uniquely owned review to the correct window and requires an explicit destination when ownership is multiple or absent; chooser success, cancellation, and timeout follow the [window proof](project-window-integration.md#first-slice-proof-and-sequencing).
- In a disposable profile, use SQLite-aware backups of both stores, restore them, and verify task-review links. Copying only a live main SQLite file is not accepted as this proof. Inspect normal and narrow native windows in light/dark modes, focus, text wrapping, tab alignment, and the bottom of scrollable content with the selected UI verification tools.

The detailed dashboard layout still needs the user's A/B/C selection. The selected C stage uses [state policy A](first-macos-task-scope.md) and still needs decisions on archive/delete retention, supported provider/account modes, agent execution environment, ordinary-folder agent eligibility, and multi-review selection. Notion authorization, connector distribution, and Windows architecture remain separate full-product requirements; none changes this checkpoint's project/task/review IDs.
