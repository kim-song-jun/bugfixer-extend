# Project dashboard and task journey

Status: proposed UI section for the macOS design. The user selected a simple dashboard, the posco-mds visual direction, native Code OSS tabs for the dashboard, editable files, and Whiteboard reviews, one native window per project, and the [C task scope with state policy A and deletion policy B](first-macos-task-scope.md). Detailed placement and remaining restore/review behavior need review with the complete design spec; no product UI has been implemented.

## Primary journey

1. **Open a project.** Relaunch restores the project windows that were open at quit. With none to restore, a project picker shows recent projects. Choosing one focuses its existing native window or opens a new window bound to that project. An unavailable folder offers **Rebind folder** in its own window. The dashboard becomes the first editor tab for a valid project.
2. **Choose work.** The dashboard shows one next action, active or waiting runs, and a compact four-state task board: Ready, In progress, Review, Done. Its next-action order follows [the run contract](architecture.md#task-board-and-run-lifecycle). This is the working surface; a second full board page would duplicate navigation.
3. **Open a task.** Selecting a card opens its details within the dashboard. The internal foundation checkpoint shows its intent, folder binding, and first linked review. The selected C task experience adds archive/restore, manual order, recoverable deletion, several review links, and a real run with its chosen provider/account, current state, and history. Deleting an active task shows that its owned runs will be cancelled first; the task enters Trash only after cleanup succeeds, with its run history and review links available on restore. A task with an available registered Git/jj checkout offers **Create review**; **Open review** selects a stored link, while creating another review is a separate action. The review follows saved worktree files and may initially have no diff. A missing or unsupported checkout explains why review creation is unavailable. Selected source snapshots, the applied convention version, and test evidence enter as their own services become available. The primary action depends on actual capability; no agent or connector control appears before its service works.
4. **Work in the same window.** A task's file opens in the native Code OSS editor tab. Its Whiteboard review opens in another native editor tab. The dashboard keeps the selected task ID independently from the file URI; a file opened from two tasks changes the visible task context explicitly. Returning to the dashboard preserves scroll position and card selection.
5. **Check and finish.** The selected C task experience shows a real run's provider, chosen account, subagent tree, live events, cancellation, and resulting files. A recorded start moves Ready to In progress and verified success moves In progress to Review; the person can inspect each triggering event and any stale-state suggestion. **Done** is a person's explicit action. A provider's exit code alone cannot finish a run or task. References show their source and retrieval time when import exists. The review and, when available, Ego Lite check are linked to the task and its run.

## Window and navigation

- Use one native Code OSS tab strip for dashboard, files, and reviews. Do not draw a second general document tab strip inside the dashboard. Adapt the posco-mds tab principles to the native strip: clear active state, readable truncation, accessible overflow, close behavior, and distinct labels for duplicate titles.
- The project switcher and task entry remain visible in the workbench's navigation area. Switching focuses or opens the other project's window without replacing the current checkout or tabs. Within the dashboard, use a compact project header, a single next-action panel, then the board. Selecting a task reveals an inspector instead of creating another top-level screen. Reference and account settings can be separate app views reached from the project/settings navigation.
- A review opened from a task shows a return path to that task. The existing Whiteboard read-only source navigator remains a distinct action for pinned historical material; it does not replace the editable project tab.
- Save the active project, task ID, dashboard position, and relevant tab identities for restart. A reused file tab never silently inherits a different task's evidence or action context. A closed or deleted review displays an unavailable link with its repair action.

## Visual system

Use the generic semantic direction of the read-only posco-mds theme reference, without importing its domain-specific content or source. For the light theme, the page/card/text/accent anchors are `#F2F4F6`, `#FFFFFF`, `#191F28`, and `#2370DE`. The dark anchors are `#17171C`, `#1E2028`, `#ECECEC`, and `#5B9FF5`. Pretendard Variable is the reference font with system fallbacks; verify redistribution rights before bundling its files in the public app. Use a 4 px spacing grid adjusted to native workbench dimensions. Prefer 8–12 px radii for standard cards and controls where appropriate; the source scale also includes smaller controls and larger panels. State meaning uses text and icons alongside color; the accent is reserved for selection and primary action. The four-state board and task inspector are this product's design, informed by the reference dashboard's hierarchy rather than copied components.

At a standard desktop width, the board can show four readable columns. At a narrow project window, columns reflow to two or one while the task inspector remains reachable without covering the primary action. Use native editor and workbench layout measurements during implementation rather than assuming a web page viewport. Respect the system light/dark choice and reduced-motion setting. Keyboard focus, selection, pending work, and errors must remain visible in both themes.

## Screen states and staged behavior

| Surface | Empty | Loading / skeleton | Error | Success |
| --- | --- | --- | --- | --- |
| Project picker | Explain how to open a local folder; **Open folder** | Recent-project rows reserve their final size | Missing/moved folder offers **Rebind folder** | Project opens to its dashboard tab |
| Dashboard | One direct **Create task** action; no decorative metrics | Board columns and task cards reserve stable space | Workspace DB failure shows cause and retry or repair path | Next action, task counts, and selected card agree with persisted data |
| Task inspector | Ask the user to choose a card | Details keep their panel bounds | Missing folder, run, or review is shown beside that link; later, the same applies to references | Task title, folder, review list, real run details, and C actions are visible together when their stage is complete |
| Trash | Explain that no tasks are deleted | Pending cancellation names the task and owned run; the task stays on the active board until cleanup finishes | Cancel/cleanup failure leaves the task visible with retry; no false Trash entry appears | Restore returns the same task ID, run history, evidence links, and review links |
| Run and subagents | State that no run exists yet | Queued work shows its reason, including a checkout writer conflict; running work shows real events | Preflight, provider, cancellation, and cleanup failures remain distinct; an unverified run after restart is **Interrupted** | Waiting for input names the decision and agent; parent/child results and cleanup outcome persist after restart |
| Convention document | Offer **Write rule** or **Draft from references** once imports work | Draft/check progress is separate from active version | Unsupported or sensitive claim points to rule and source | Reasons, good/avoided examples, source links, diff, and **Apply** are readable |
| Reference import | Show Slack, Notion, website, and installed connector entry points when live | Retrieval progress retains source identity | Auth, permission, and fetch errors name the affected source | Before installing a declarative connector, show its domains and account scopes; the first-release package has no local file, browser API, or executable-code capability. After import, snapshot origin, retrieval time, and version are visible before attachment |
| E2E evidence | Offer a check only when Ego Lite is available | Target and task-space state remain visible | Scenario failure and cleanup failure use separate messages | Screenshot, console/network findings, target, verdict, and cleanup result are linked |

No disabled placeholder buttons advertise a service that does not yet exist. A skeleton represents a pending request with stable geometry; it is not the default appearance for an empty project. When a section is not part of the current implementation slice, its entry point is absent until its backing contract works.

## Validation when implemented

The foundation UI proof opens two projects in separate windows, creates a task, saves a file, opens its linked review in that same project's window, switches between projects, and restores both windows after restart without swapping tabs or active tasks. It also opens one file from two tasks in a project to prove task-context isolation. The selected C proof additionally covers archive/restore, manual order, several reviews, live run/cancellation, audited automatic transitions, and deletion policy B: owned-run cancellation, cleanup failure, Trash entry, and restoration of the same links. Inspect before/after native screenshots at normal and narrow window widths, keyboard focus, text wrap, contrast, tab alignment, and the bottom of scrollable content. Connector, convention, and E2E journeys add their own screenshots and console/network evidence when implemented. Start UI verification with ego-browser on reachable app and web surfaces; use computer-use inspection for native shell behavior that a browser cannot expose. Ego Lite checks the web target and its task-space cleanup.
