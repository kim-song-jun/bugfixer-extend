## Primary journey

1. **Open a project.** Relaunch restores the project windows that were open at quit. With none to restore, a project picker shows recent projects. Choosing one focuses its existing native window or opens a new window bound to that project. An unavailable folder offers **Rebind folder** in its own window. The dashboard becomes the first editor tab for a valid project.
2. **Choose work.** The dashboard shows one next action, active or waiting runs, and a compact four-state task board: Ready, In progress, Review, Done. Its next-action order follows [the run contract](architecture.md#task-board-and-run-lifecycle). This is the working surface; a second full board page would duplicate navigation.
3. **Open a task.** Selecting a card opens its details within the dashboard. The current partial UI supports task editing, manual state and order changes, archive/restore, and Trash/restore. Trash asks for confirmation; the app cancels the task's owned runs and waits for cleanup. If cancellation or cleanup fails, the task stays on the board with its error and retry path. Native UI flow QA has exercised this task lifecycle. The rest of the selected C experience remains open: several review links, a real mutating run with its chosen provider/account, current state, and history. A task with an available registered Git/jj checkout offers **Create review**. All linked reviews are visible; **Open review** opens the task's person-chosen primary, each row opens its own review, and **Create another review** is a distinct action that does not change the primary. An unavailable primary stays marked for repair or reselect. The review follows saved worktree files and may initially have no diff. An ordinary non-VCS folder still offers an agent run after folder-specific mutation enablement and a real permission preview, but explains why Whiteboard review and Git rollback are unavailable. A missing folder blocks execution and offers rebind. Selected source snapshots, the applied convention version, and test evidence enter as their own services become available. The primary action depends on actual capability; no agent or connector control appears before its service works.
4. **Work in the same window.** A task's file opens in the native Code OSS editor tab. Its Whiteboard review opens in another native editor tab. The dashboard keeps the selected task ID independently from the file URI; a file opened from two tasks changes the visible task context explicitly. Returning to the dashboard preserves scroll position and card selection.
5. **Check and finish.** The selected C task experience shows a real run's provider, chosen account, subagent tree, live events, cancellation, and resulting files. A recorded start moves Ready to In progress and verified success moves In progress to Review; the person can inspect each triggering event and any stale-state suggestion. For an ordinary non-VCS task, the next action in Review is **Inspect changes**: open the in-root changed-path report and files, with symlink targets and out-of-root writes marked unverified. This board state does not create a Whiteboard review. **Done** is a person's explicit action. A provider's exit code alone cannot finish a run or task. References show their source and retrieval time when import exists. Any available Whiteboard review and Ego Lite check are linked to the task and its run.

## Window and navigation

- Use one native Code OSS tab strip for dashboard, files, and reviews. Do not draw a second general document tab strip inside the dashboard. Adapt the posco-mlip tab principles to the native strip: clear active state, readable truncation, accessible overflow, close behavior, and distinct labels for duplicate titles.
- The project switcher and task entry remain visible in the workbench's navigation area. Switching focuses or opens the other project's window without replacing the current checkout or tabs. Within the dashboard, use a compact project header, a single next-action row, then the full-width board. Selecting a task reveals a section below the board instead of narrowing all four lanes or creating another top-level screen. The reference and convention sidebar entries replace the board content with their own sections in the same native tab; account controls live with references.
- A review opened from a task shows a return path to that task. The existing Whiteboard read-only source navigator remains a distinct action for pinned historical material; it does not replace the editable project tab.
- Save the active project, task ID, dashboard position, and relevant tab identities for restart. A reused file tab never silently inherits a different task's evidence or action context. A closed or deleted review displays an unavailable link with its repair action.

## Visual system

Use the generic semantic direction of the read-only posco-mlip theme reference, without importing its domain-specific content, logo, or source components. For the light theme, the page/surface/text/primary/secondary/border anchors are `#F5F5F2`, `#FFFFFF`, `#222222`, `#01588B`, `#19B0E8`, and `#E4E4E0`; `#FAFAF8` is the quiet nested surface. The dark theme derives accessible counterparts because the reference does not provide a native dark app surface. Pretendard Variable is the reference font with system fallbacks; verify redistribution rights before bundling its files in the public app. Use a 4 px spacing grid adjusted to native workbench dimensions and 8/12/16 px radii for controls, sections, and larger panels. Reserve bordered white panels for peer-level dashboard sections. Use headings, spacing, dividers, and quiet rows within them; avoid putting rounded cards inside rounded cards. State meaning uses text and icons alongside color; primary navy marks selection and action while cyan is a restrained supporting accent. The four-state board and task inspector are this product's design, informed by the reference dashboard's hierarchy rather than copied components.

At a standard desktop width, the board can show four readable columns separated by quiet dividers, with flat task rows. At a narrow project window, columns reflow to two or one while the task detail remains reachable without covering the primary action. The selected detail must not make the board columns too narrow to read. Use native editor and workbench layout measurements during implementation rather than assuming a web page viewport. Respect the system light/dark choice and reduced-motion setting. Keyboard focus, selection, pending work, and errors must remain visible in both themes.
