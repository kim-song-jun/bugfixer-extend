## Workspace database slice

The macOS Code OSS main process opens `workspace.db` under its user-data profile and closes it during shutdown. The database owns projects, folder bindings, tasks and board order, immutable Review command outbox rows, task-to-review links, and project views. SQLite foreign keys reject cross-project task bindings and selected-task views. Rebinding a folder clears its old VCS and Review identity, and a later registration requires the path observed during verification. Renderer project authorization and task create/edit/order/lifecycle IPC now use this main-process-owned store; Review API writes and receipt recovery remain unimplemented.

On an isolated temporary macOS profile, the development app created schema version 1 with six tables, launched successfully, and returned HTTP 200 with `ok: true` and `desktopAttached: true` from the Review health endpoint. A second isolated profile with an invalid `workspace.db` displayed the native “Workspace data unavailable” dialog and exited without replacing the invalid file. The focused database suite passed 10 tests, Code OSS `typecheck-client` passed, and the development compile passed. These checks establish the storage and startup slice only; they do not satisfy row 3's Review write/recovery and project-window requirements.

## Open choices versus missing evidence

User decisions still required: Antigravity subscription scope; Notion authorization; signed-in website capture; connector package distribution and credential UX; and the later Windows CPU target. First-release account mode A, native macOS execution mode A, dashboard layout A, and selected C task policies are recorded in the UX and task-scope documents. Broader provider multi-account behavior remains an acceptance objective, not a selected first-release mode. The design documents and local comparison artifacts may recommend an option, but no recommendation is an approval.

A first-release limitation on one provider's accounts does not remove the user's broader multi-account objective. Row 5 stays open for any provider that lacks the requested multi-account behavior until the capability is proven or the user explicitly revises that objective.

Even after these choices, every row above remains unaccepted until the actual code and named runtime proof exist. The [discovery inventory](discovery.md#product-requirements-to-preserve) preserves the original product scope, while the linked contracts define how to verify each part without treating the internal foundation or C task slice as the finished product.
