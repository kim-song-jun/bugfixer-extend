## Workspace database slice

The macOS Code OSS main process opens `workspace.db` under its user-data profile and closes it during shutdown. The database owns projects, folder bindings, tasks and board order, immutable Review command outbox rows, task-to-review links, provider attempts/events, reference snapshots, convention versions, connector metadata, and E2E evidence. SQLite foreign keys and project-window authorization enforce ownership. Rebinding a folder clears its old VCS and Review identity, and Review operations verify checkout identity before using a link. Main-process channels provide task lifecycle, provider-run, Review bridge, reference/connector, convention, and E2E operations; focused database, gateway, and subsystem tests cover important contracts. The supplied current verification includes three gateway tests, native bound-checkout/Keychain tests, typecheck, compile, and local unsigned macOS package verification. Live two-window conflict/recovery and dual-store backup/restore acceptance remain unverified.

Earlier isolated-profile checks established database startup, invalid-database handling, and Review health. Current source and gateway tests additionally cover Review create/list/open/primary operations; the supplied isolated QA includes three gateway tests. Neither evidence set proves dual-store backup/restore, all lost-response recovery cases, or project-window restoration and routing required by row 3.

## Open choices versus missing evidence

Remaining product choices or proof: Notion authorization details, signed-in website capture beyond user-selected Ego text, connector package distribution/credential UX, and the later Windows CPU target. First-release account mode A, native macOS execution mode A, dashboard layout A, and selected C task policies are recorded in the UX and task-scope documents. Broader provider multi-account behavior remains an acceptance objective, not a selected first-release mode. The design documents and local comparison artifacts may recommend an option, but no recommendation is an approval.

A first-release limitation on one provider's accounts does not remove the user's broader multi-account objective. Row 5 stays open for any provider that lacks the requested multi-account behavior until the capability is proven or the user explicitly revises that objective.

Implementation presence, focused tests, isolated-app QA, and packaged-product acceptance are distinct evidence levels. Rows remain open only for the specific runtime or product proof named in their current boundary; completed code paths and tests should not be relabeled unimplemented. The [discovery inventory](discovery.md#product-requirements-to-preserve) preserves the original product scope, while the linked contracts define how to verify each part without treating the internal foundation or C task slice as the finished product.
