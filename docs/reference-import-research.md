# Reference import source and authorization research

Status: source-backed research for the macOS design, not an approved choice of Notion authorization or signed-in website capture. The selected product scope is first-party Slack, Notion, and website import plus user-installable **declarative** connectors. No importer, OAuth client, or credential store is implemented in this repository. The common immutable snapshot and agent-instruction boundary is in [architecture.md](architecture.md#imported-reference-and-connector-contract).

## Common user action and stored evidence

The import flow starts from a person-selected source item or URL and previews the exact material to attach to a project task. The app records the source account reference, stable source identity, canonical link, retrieval time, connector and parser version, content hash, original response or captured-page artifact, and any explicit omissions. Each successful refresh creates a linked immutable snapshot even when its content hash matches the prior one; prior task and convention evidence stays readable. The app does not infer that a source link or OAuth grant authorizes importing every accessible item.

An importer must identify **complete**, **partial**, **unavailable**, and **needs reconnection** outcomes. It must not display a partial thread or page as a complete snapshot. Text extracted for an agent is a derived artifact with source labels; it never becomes a project rule or instruction without the user's explicit Apply or promotion action. Tokens, refresh tokens, cookies, and OAuth code verifiers belong in a credential mechanism separate from `workspace.db` and source artifacts.

## Slack first-party import

[Slack's PKCE flow](https://docs.slack.dev/authentication/using-pkce/) supports a public desktop client without embedding a `client_secret`. A desktop redirect can request **user scopes**, not bot scopes; PKCE refresh tokens rotate and expire after 30 days, so the app needs a visible reconnect path. A reading connection requests only the relevant conversation `*:history` scope for the conversation types it supports. Actual access still depends on the account's membership and workspace policy. This is a proposed native authorization route, not an account connection already tested in the app.

For a selected message, the source key includes workspace/team ID, conversation ID, and message `ts`. [Slack `conversations.replies`](https://docs.slack.dev/reference/methods/conversations.replies/) accepts a conversation ID and parent-message `ts`, returning a cursor-paginated thread; an unthreaded message returns alone. [Slack `chat.getPermalink`](https://docs.slack.dev/reference/methods/chat.getPermalink/) provides a shareable message link. Store the message and reply IDs in order and preserve the returned JSON artifact alongside readable text. A file reference is marked as metadata-only unless a separate `files:read` grant and download contract are implemented; a missing binary is not represented as captured content.

Slack's [history](https://docs.slack.dev/reference/methods/conversations.history/) and [replies](https://docs.slack.dev/reference/methods/conversations.replies/) pages document a one-request-per-minute, 15-object limit for **new commercially distributed non-Marketplace apps**; Marketplace and internal customer-built apps have a different tier. The app must not assume one fixed quota. It follows `Retry-After`, bounds retries, resumes a cursor without duplicating evidence, and checks Slack's `ok` field even when HTTP succeeds. The release proof uses a message plus a thread spanning two pages and a rate-limited response; it never claims an incomplete page is a whole thread.

## Notion first-party import and authorization seam

The REST [page endpoint](https://developers.notion.com/reference/retrieve-a-page) supplies page metadata; [block children](https://developers.notion.com/reference/get-block-children) supplies a paginated first level. A complete text/page capture must follow `next_cursor` and descend into nested blocks. The app records the page UUID, page URL, block IDs, and raw response artifacts before deriving a readable document. It shows an omission when a property, attachment, or inaccessible block is not captured. The current Notion API documentation requires a `Notion-Version` header; the version used by an importer must be recorded with each snapshot. [Notion's current rate-limit guidance](https://developers.notion.com/reference/request-limits) requires honoring `Retry-After` for 429 and 529 responses.

The authorization route remains a user decision because the official paths have different product boundaries:

| Route | Official capability | Product consequence |
| --- | --- | --- |
| REST public connection | [Notion public OAuth](https://developers.notion.com/guides/get-started/authorization) lets a person pick shared pages, but code exchange and refresh require the connection's `CLIENT_SECRET`. [Capabilities](https://developers.notion.com/reference/capabilities) allow Read content without write access. | A public desktop binary must not embed that secret. A separately operated OAuth and refresh broker would be needed for the product's own public connection; it can request provider-enforced read-only access and keep REST page/block semantics. |
| Notion-hosted MCP | [Notion MCP client guidance](https://developers.notion.com/guides/mcp/build-mcp-client) documents PKCE and dynamic client registration with `token_endpoint_auth_method: none`; [the fetch tool](https://developers.notion.com/guides/mcp/mcp-supported-tools) reads a selected URL or ID. | No product OAuth server is needed, but [the connection can read and update content](https://developers.notion.com/guides/mcp/overview). An app-side read-tool allowlist does not reduce the remote grant if the credential is stolen. `notion-fetch` can truncate large pages and report omitted subtree IDs, so completeness and artifact shape need a live proof. |
| User-provided local token | [Notion internal connections](https://developers.notion.com/guides/get-started/authorization) use a static token and require a workspace owner to create the connection and manually share pages; [Read content capability](https://developers.notion.com/reference/capabilities) can restrict it to reads. A personal access token acts as its owner and has no OAuth page picker. | No product OAuth server is needed, but setup is manual. Prefer an internal read-only connection for controlled/pilot users; a PAT has the user's workspace reach and is not the default path for a public product. Neither is a silent fallback for a failed OAuth connection. |

The first Notion proof needs one selected page spanning more than one pagination cursor and containing a nested block, then a changed page that leaves the earlier snapshot intact. The selected route must establish what “complete” means for its response and show a visible partial state if it cannot recover an omitted subtree. Refresh-token rotation, if used, needs one serialized refresh per connection and an atomic token-pair update; [Notion documents rotation and `invalid_grant` recovery](https://developers.notion.com/guides/mcp/build-mcp-client).

## Website import and signed-in capture seam

A public URL can be fetched through an app-owned request with **no ambient browser credentials**, then labeled with the requested URL, final URL, retrieval time, parser version, content type, and omitted assets. URL validation and every redirect must follow the chosen host/network policy; [OWASP's SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) identifies redirects and DNS changes as bypass risks. HTML text is source data and may contain hostile instructions; it is never executed as a connector package or treated as an agent command.

Signed-in pages require a separate user action. [Electron sessions](https://www.electronjs.org/docs/latest/api/session) can isolate an app-owned login from the user's unrelated browser profile; an explicit **Capture this page** action could snapshot the current tab after a preview. [Electron's security guidance](https://www.electronjs.org/docs/latest/tutorial/security) requires a sandbox, context isolation, limited permissions, and constrained navigation/IPC for remote content. A [Chrome `activeTab` extension](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) is another explicit-capture path, but adds separate browser distribution and app handoff. The chosen v1 capture path, session retention, and the meaning of a user-approved page selection remain open; public URL import alone does not imply access to a signed-in browser session.

## Selected declarative package boundary

An installed connector remains data interpreted by trusted app code, as specified in [connector-runtime.md](connector-runtime.md#selected-a-contract-and-release-proof). Its package can declare supported hosts, endpoint templates, parameters, and bounded response-field mappings. It cannot run JavaScript, read local files or browser cookies, or obtain tokens directly. The app resolves requests through a broker that checks the declared host and account on every request, including redirects. [RFC 6901 JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) is a candidate for simple response-field selection without expression evaluation; the exact schema, supported authentication modes, package signing/distribution, and limits still need design. A REST source that requires custom logic or unsupported OAuth is reported as unsupported rather than receiving a hidden executable escape hatch.

## Decisions and verification still required

1. Select the Notion authorization route after reviewing the one-click setup, remote grant, data-completeness, and service-operation trade-offs. Do not infer a REST OAuth result from an MCP login.
2. Select the signed-in website capture route separately from anonymous public URL import.
3. Define the declarative package schema, supported host-owned credentials, and installation channel without granting executable capabilities.
4. Prove each source against a real account or controlled test workspace during implementation; official API documentation is not runtime evidence for the packaged Whiteboard fork.
