# Reference import source and authorization research

Status: selected scope is basic first-party Slack and Notion import, public web URL import, and signed-in selected-text capture through Ego. The capture choice replaces Chrome. Local installation of signed declarative connector packages and public website URL preview/import are implemented in source with focused tests. The user selected **A — a user-provided Notion personal access token (PAT)** for the first-party Notion importer. The local app keeps it in macOS Keychain and labels each workspace connection; this choice does not add a Notion OAuth server or change installed-package account mode B. Packaged macOS proof covers preview, task-linked save, refresh, and restart restore for `https://example.com/`, plus Ego selected-text import from a user-selected local page into a task-linked immutable reference. Real Slack/Notion account imports, signed-in remote capture, Notion completeness on a real account, and remaining security/release proofs are unverified. The common immutable snapshot and agent-instruction boundary is in [architecture.md](architecture.md#imported-reference-and-connector-contract).

## Common user action and stored evidence

The import flow starts from a person-selected source item or URL and previews the exact material to attach to a project task. The app records the source account reference, stable source identity, canonical link, retrieval time, connector and parser version, content hash, original response or captured-page artifact, and any explicit omissions. Each successful refresh creates a linked immutable snapshot even when its content hash matches the prior one; prior task and convention evidence stays readable. The app does not infer that a source link or OAuth grant authorizes importing every accessible item.

An importer must identify **complete**, **partial**, **unavailable**, and **needs reconnection** outcomes. It must not display a partial thread or page as a complete snapshot. Text extracted for an agent is a derived artifact with source labels; it never becomes a project rule or instruction without the user's explicit Apply or promotion action. Tokens, refresh tokens, cookies, and OAuth code verifiers belong in a credential mechanism separate from `workspace.db` and source artifacts.

## Slack first-party import

[Slack's PKCE flow](https://docs.slack.dev/authentication/using-pkce/) supports a public desktop client without embedding a `client_secret`. A desktop redirect can request **user scopes**, not bot scopes; PKCE refresh tokens rotate and expire after 30 days, so the app needs a visible reconnect path. A reading connection requests only the relevant conversation `*:history` scope for the conversation types it supports. Actual access still depends on the account's membership and workspace policy. This is a proposed native authorization route, not an account connection already tested in the app.

For a selected message, the source key includes workspace/team ID, conversation ID, and message `ts`. [Slack `conversations.replies`](https://docs.slack.dev/reference/methods/conversations.replies/) accepts a conversation ID and parent-message `ts`, returning a cursor-paginated thread; an unthreaded message returns alone. [Slack `chat.getPermalink`](https://docs.slack.dev/reference/methods/chat.getPermalink/) provides a shareable message link. Store the message and reply IDs in order and preserve the returned JSON artifact alongside readable text. A file reference is marked as metadata-only unless a separate `files:read` grant and download contract are implemented; a missing binary is not represented as captured content. Slack import is selected scope, but no real Slack account import has been demonstrated.

Slack's [history](https://docs.slack.dev/reference/methods/conversations.history/) and [replies](https://docs.slack.dev/reference/methods/conversations.replies/) pages document a one-request-per-minute, 15-object limit for **new commercially distributed non-Marketplace apps**; Marketplace and internal customer-built apps have a different tier. The app must not assume one fixed quota. It follows `Retry-After`, bounds retries, resumes a cursor without duplicating evidence, and checks Slack's `ok` field even when HTTP succeeds. The release proof uses a message plus a thread spanning two pages and a rate-limited response; it never claims an incomplete page is a whole thread.

## Notion first-party import and authorization seam

The REST [page endpoint](https://developers.notion.com/reference/retrieve-a-page) supplies page metadata; [block children](https://developers.notion.com/reference/get-block-children) supplies a paginated first level. A complete text/page capture must follow `next_cursor` and descend into nested blocks. The app records the page UUID, page URL, block IDs, and raw response artifacts before deriving a readable document. It shows an omission when a property, attachment, or inaccessible block is not captured. The current Notion API documentation requires a `Notion-Version` header; the version used by an importer must be recorded with each snapshot. [Notion's current rate-limit guidance](https://developers.notion.com/reference/request-limits) requires honoring `Retry-After` for 429 and 529 responses.

The product selected basic Notion import using a user-provided PAT. The app implements the PAT connection path, but no real-account import has been demonstrated. The official routes have different product boundaries:

| Route | Official capability | Product consequence |
| --- | --- | --- |
| REST public connection | [Notion public OAuth](https://developers.notion.com/guides/get-started/authorization) lets a person pick shared pages, but code exchange and refresh require the connection's `CLIENT_SECRET`. [Capabilities](https://developers.notion.com/reference/capabilities) allow Read content without write access. | A public desktop binary must not embed that secret. A separately operated OAuth and refresh broker would be needed for the product's own public connection; it can request provider-enforced read-only access and keep REST page/block semantics. |
| Notion-hosted MCP | [Notion MCP client guidance](https://developers.notion.com/guides/mcp/build-mcp-client) documents PKCE and dynamic client registration with `token_endpoint_auth_method: none`; [the fetch tool](https://developers.notion.com/guides/mcp/mcp-supported-tools) reads a selected URL or ID. | No product OAuth server is needed, but [the connection can read and update content](https://developers.notion.com/guides/mcp/overview). An app-side read-tool allowlist does not reduce the remote grant if the credential is stolen. `notion-fetch` can truncate large pages and report omitted subtree IDs, so completeness and artifact shape need a live proof. |
| User-provided personal access token (selected A) | [Notion PATs](https://developers.notion.com/guides/get-started/personal-access-tokens) act with the creator's workspace membership and page permissions; pages do not need to be shared with a bot. The Notion API capability includes both reading and changing content, without a PAT-specific read-only choice. | The user creates an app-specific PAT and pastes it into the local app; the token stays in macOS Keychain. The importer sends read requests for the selected page, while the credential itself can reach other pages the user can access. No product OAuth server or page picker is required. The app must explain the broader token permission, expiry, and revocation. |

No real Notion account import has been demonstrated. Proof needs one selected page spanning more than one pagination cursor and containing a nested block, then a changed page that leaves the earlier snapshot intact. The selected PAT route must establish what “complete” means for its response and show a visible partial state if it cannot recover an omitted subtree. A PAT expires and requires a new token to reconnect; it has no OAuth refresh-token rotation. [Notion documents PAT expiry and revocation](https://developers.notion.com/guides/get-started/personal-access-tokens).

## Website import and signed-in capture seam

The source implements public URL preview/import through an app-owned request with **no ambient browser credentials**. It records requested and final URLs, retrieval time, importer version, content type, and extraction omissions with an immutable content snapshot. URL validation and every redirect recheck public DNS answers and use pinned addresses; focused tests cover private destinations and redirect revalidation. A packaged macOS run previewed and saved `https://example.com/`, linked it to a task, refreshed it into v2, and restored both versions after restart. This establishes the packaged example-page flow, but not the broader security matrix or every public-page case. [OWASP's SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) identifies redirects and DNS changes as bypass risks. HTML text is source data and may contain hostile instructions; it is never executed as a connector package or treated as an agent command.

Signed-in capture uses the selected-text path through Ego; the user explicitly replaced the Chrome extension option. This is a distinct user action and captures only the selected text, with a preview and source attribution. A packaged macOS run imported selected text from a user-selected local page into a task-linked immutable reference and closed the product-created TaskSpace. This does not prove remote signed-in capture or access to a browser's ambient session. [Electron's security guidance](https://www.electronjs.org/docs/latest/tutorial/security) requires a sandbox, context isolation, limited permissions, and constrained navigation/IPC for remote content where remote content is involved.

## Selected declarative package boundary

Local installation of signed declarative connector packages is implemented in source. The package remains data interpreted by trusted app code, as specified in [connector-runtime.md](connector-runtime.md#selected-a-contract-and-release-proof); installation alone does not prove every runtime security boundary. Packages declare supported hosts, endpoint templates, parameters, and bounded response-field mappings. They cannot run JavaScript, read local files or browser cookies, or obtain tokens directly. The app resolves requests through a broker that checks the declared host and account on every request, including redirects. [RFC 6901 JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) is a candidate for simple response-field selection without expression evaluation; supported authentication modes, signing/distribution and security proof still need validation. A REST source that requires custom logic or unsupported OAuth is reported as unsupported rather than receiving a hidden executable escape hatch.

## Decisions and verification still required

1. Verify the selected Notion PAT setup and live import with a real account, including expiry/reconnect, permission disclosure, data completeness, and the immutable snapshot. Do not infer a REST account result from an MCP login.
2. Packaged macOS proof already covers preview/save/refresh/restore for `https://example.com/` and Ego selected-text import from a user-selected local page. Extend verification to a broader public-page sample and the URL/redirect/SSRF boundaries beyond the focused tests; prove remote signed-in capture separately if that capability is required.
3. Continue validating the implemented local signed declarative package install against its schema, signature, host/account broker checks, and no-executable-capability contract.
4. Prove each source against a real account or controlled test workspace; official API documentation is not runtime evidence for the packaged Whiteboard fork. Real Slack and Notion account imports and remote signed-in Ego capture have not been demonstrated.
