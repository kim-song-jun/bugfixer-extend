# Provider run and instruction adapters

Status: researched adapter contract for the macOS design, not an implemented integration or proof of authenticated account isolation. It extends the selected [run lifecycle](architecture.md#task-board-and-run-lifecycle) and [app-authored convention document](architecture.md#selected-conventions-app-authored-project-document). Antigravity subscription-account scope is still a user decision.

## Local and documented capabilities

The installed help/version commands inspected on 2026-09-26 reported Claude Code `2.1.283`, Codex CLI `0.157.1`, and Antigravity CLI `1.2.3`. No credential files were opened and no authenticated run was started. These versions are observations, not a pinned application dependency yet.

| Adapter | Headless event path | Resume identity | Account boundary to prove |
| --- | --- | --- | --- |
| Claude Code | [`claude -p --output-format stream-json`](https://code.claude.com/docs/en/cli-reference) | Provider session ID via `--resume` or `--continue`; `--no-session-persistence` prevents later resume | [`CLAUDE_CONFIG_DIR`](https://code.claude.com/docs/en/env-vars) separates configuration directories for side-by-side accounts; prove two distinct logins and simultaneous identity retention |
| Codex CLI | [`codex exec --json`](https://learn.chatgpt.com/docs/non-interactive-mode) emits JSONL; `--output-schema` constrains the final answer | Provider thread/session ID via `codex exec resume` | [`CODEX_HOME`](https://developers.openai.com/codex/config-advanced) relocates state; [credentials](https://developers.openai.com/codex/config-reference) may use a file or OS keyring, so separate homes alone do not prove account isolation |
| Antigravity CLI | [`agy -p --output-format stream-json`](https://www.antigravity.google/docs/cli/headless/) emits step updates and a terminal result | Conversation ID via `--conversation` or `--continue` | [Signed-in profile](https://antigravity.google/docs/cli-install?hl=en) uses the OS keyring; no documented per-run subscription-account selector was found. Gemini API-key mode is a separate billing/authentication choice |

The provider session/conversation ID is stored separately from the app's immutable run ID. A resumed provider conversation creates a new app attempt linked to its prior attempt; it never overwrites the original prompt, account, event stream, or result. The adapter parses provider events while streaming. Its persisted event schema allowlists state, timestamps, provider IDs, usage, and other non-content metadata; tool parameters/output and model text are sensitive content, not safe merely because an event was normalized. Content is stored only through the app's redaction and artifact policy. Raw stdout/stderr is not automatically saved. The mapping needs versioned parsers so an upgraded CLI cannot silently turn an unfamiliar terminal event into success.

## One-run launch contract

1. Persist the launch snapshot before spawning: task and checkout IDs, canonical worktree, provider/CLI version, selected account reference, working directory, selected model/role, permission mode, active convention version, rendered prompt hash and text, selected reference snapshot IDs, parent run ID, and requested tool capabilities. The app never writes credential values to `workspace.db` or the run log.
2. Preflight the checkout, account profile, required tool permissions, convention payload, and execution environment. An account label is not identity proof. Provider-specific profile isolation must pass a real credential-isolation smoke test before the UI claims concurrent accounts for that mode. Unavailable or unverified modes remain explicit rather than silently switching to another account or billing method.
3. Spawn the CLI with an argument array and a per-run environment, in the selected checkout directory. Capture stdout and stderr as bounded streams and parse documented events. Persist only allowlisted event metadata and terminal fields; any tool input/output or model text must pass credential redaction and the separate content-artifact policy before persistence. If that check cannot classify content, keep it transient and record only a redacted summary and hash. The app must not infer success from process exit code alone: [Antigravity headless permissions can soft-deny tools and still exit `0`](https://www.antigravity.google/docs/cli/headless/).
4. Record a provider session/conversation ID when it arrives. Show queue, preflight, running, waiting for input, succeeded, failed, cancelled, and interrupted as separate states. A missing terminal event, parse failure, or process crash is not success. Provider internals are not independently managed subagents unless the adapter exposes verifiable child lifecycle data; app-owned subagents are child runs with their own snapshots.
5. Cancellation targets only the owned provider process tree and execution resources. Give the provider a documented graceful signal or command when available, then bounded TERM and precise KILL if needed, and record the terminal event, process exit, cleanup, and any checkout changes separately. A restart without a verified live process marks the attempt interrupted; resume is an explicit new attempt only after the provider's behavior has been tested.

Provider permission controls differ: [Claude Code](https://code.claude.com/docs/en/cli-reference) exposes permission mode and tool allow/deny flags, [Codex](https://learn.chatgpt.com/docs/developer-commands?surface=cli) exposes sandbox and approval controls, and [Antigravity](https://www.antigravity.google/docs/cli/headless/) has headless permission rules. The UI should describe the chosen provider's effective capability set, not display one generic switch that implies equivalent guarantees. Antigravity documents `SUCCESS`, `ERROR`, `CANCELED`, `INTERRUPTED`, `INVALID`, `WAITING`, and `RUNNING` result statuses. Only `SUCCESS` with no unmet required-tool operation can map to app success; `INVALID` is a failure and `RUNNING` is incomplete even if a result envelope was emitted. The other statuses retain distinct app states.

## Convention delivery and visibility

When a project has an applied version, the app renders one clearly labeled **Project conventions** section into that run's prompt, alongside separately labeled task instructions and quoted reference material. With no applied version, the preview and run snapshot record a null convention version and an empty convention payload; no placeholder rule is sent. The app records the exact outgoing text, ordering, hash, CLI flags, checkout, and delivery path. This route does not create or overwrite native instruction files in the checkout. It also leaves each provider's normal discovery enabled. Claude's documented [`--append-system-prompt`](https://code.claude.com/docs/en/cli-reference) is a possible provider-specific higher-authority mode, but it has different precedence and resume behavior; the common contract does not silently select it. A provider conversation may resume only with the same convention snapshot and digest. If the active version changed, the app starts a fresh provider conversation, or lets the person explicitly continue the old snapshot with a warning; it never claims that a newly sent version replaced prior conversation instructions.

Native instructions still matter. [Claude Code](https://code.claude.com/docs/en/memory) can load managed, user, project, imported, and local `CLAUDE.md`/rule content; [Codex](https://developers.openai.com/codex/guides/agents-md) discovers global and path-specific `AGENTS.override.md` or `AGENTS.md`; [Antigravity](https://www.antigravity.google/docs/rules/) combines workspace, directory, global, and plugin rules with trigger and size limits. Their order and authority are not equivalent. The app can show its outgoing payload and the native file inventory it was able to inspect, but cannot claim to know the complete model context from that alone. Missing visibility, conflicts, truncation risk, and provider-specific loading evidence appear beside the pre-run preview and saved run snapshot.

Claude documents an `InstructionsLoaded` hook and `/context` inspection in its [memory guide](https://code.claude.com/docs/en/memory), which can strengthen the observed native-file list. No comparable complete, machine-verifiable context attestation is established for Codex or Antigravity here. A provider's answer about what it read is diagnostic evidence, not proof that the full native context was delivered. Reusing a Claude session also matters: its [system-prompt flags are recorded on the first request and may not change on resume until compaction](https://code.claude.com/docs/en/cli-reference). The per-run user-prompt section avoids treating a changed system-prompt flag as immediately applied on a resumed session.

## First real adapter proof

Use a disposable checkout with harmless instructions and normal native discovery. For each provider, verify a noninteractive run from the intended working directory, the exact app convention section delivered once, parsed live and terminal events, provider session ID persistence, permission-denial reporting, cancellation/cleanup, and explicit resume as a new attempt. Compare the saved preview with the actual outgoing bytes. Apply a new convention version between attempts and prove that resume retains the old snapshot or starts a fresh provider conversation, never displaying mixed context as the new version alone. Check native-file visibility separately and label any unverified provider loading. For every account mode claimed as concurrent, authenticate two accounts of the same provider in distinct app-owned profiles and run them simultaneously on separate checkouts without either run changing the other's credential state. Do not present numerical plan concurrency as proven by an adapter test.

This proof requires actual authenticated use and provider entitlements; the present help/documentation review cannot establish it. The app must not offer an unverified provider/account mode as if it passed.
