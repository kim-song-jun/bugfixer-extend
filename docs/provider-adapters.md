# Provider run and instruction adapters

Status: source now implements native Codex and Claude task-run paths, app-owned child runs, and convention draft/check/apply flows alongside the read-only connection test. The selected first actual account mode uses one existing local profile per provider; concurrent account isolation is not claimed. Reference-only convention drafting/checking is Claude-only because Codex blocks that operation. Antigravity (`agy`) execution is not implemented. Live evidence is limited to isolated real Codex and Claude task runs and one Claude convention draft/check/apply flow; this does not establish all launch-contract scenarios below. The contract extends the selected [run lifecycle](architecture.md#task-board-and-run-lifecycle) and [app-authored convention document](architecture.md#selected-conventions-app-authored-project-document). Antigravity subscription-account scope remains a user decision.

## Local and documented capabilities

The installed help/version commands inspected on 2026-09-26 reported Claude Code `2.1.283`, Codex CLI `0.157.1`, and Antigravity CLI `1.2.3`. These versions are observations, not a pinned application dependency. The isolated Codex and Claude task runs provide real runtime evidence for those selected existing local profiles; they do not prove concurrent account isolation or the full matrix of launch-contract cases. No real Slack or Notion account run has been demonstrated, and there is no packaged Ego capture proof.

The provider session/conversation ID is stored separately from the app's immutable run ID. A resumed provider conversation creates a new app attempt linked to its prior attempt; it never overwrites the original prompt, account, event stream, or result. The adapter parses provider events while streaming. Its persisted event schema allowlists state, timestamps, provider IDs, usage, and other non-content metadata; tool parameters/output and model text are sensitive content, not safe merely because an event was normalized. Content is stored only through the app's redaction and artifact policy. Raw stdout/stderr is not automatically saved. The mapping needs versioned parsers so an upgraded CLI cannot silently turn an unfamiliar terminal event into success.

## Implemented provider and convention paths

The project dashboard exposes Codex and Claude through the native project-window UI. It has a **read-only connection test** against the selected local CLI profile and separate mutating task-run actions. The main-process channels recheck task/folder/profile context, persist run snapshots and event metadata, and supervise provider processes, cancellation, and cleanup. Task runs are distinct from `connectionTest` attempts and may drive the selected automatic board transitions under the task-run contract. Real isolated task runs have been performed for both Codex and Claude; this is live evidence for basic real execution, not proof of every identity-race, cancellation, restart, permission-denial, or resource-cleanup scenario in the acceptance contract.

The app also implements convention draft, check, and apply flows. One live Claude flow has completed draft/check/apply. Reference-only convention drafting/checking is Claude-only because Codex blocks that operation. The source flow and that one runtime demonstration do not establish parity across providers or all convention visibility/resume criteria.

The implemented provider adapter set is limited to Codex and Claude. Antigravity is documented as a possible CLI adapter, but there is no `agy` launch path or run. The source includes mutating task execution, pre-run permission review, ordinary-folder grants and change reports, task-driven state updates, and app-owned subagent paths. The broader acceptance proof below remains open. Provider command/parser and lifecycle tests establish focused code contracts only; they do not establish account isolation, all native runtime edge cases, or the broader proof listed below. The app has one local profile per provider and makes no concurrent account-isolation claim.

## One-run launch contract

1. Persist the launch snapshot before spawning: task and folder-binding IDs, canonical host target root and selected working-directory path/filesystem identities, nullable VCS identity, provider/CLI version, selected account reference, selected model/role, effective permission mode, active convention version, rendered prompt hash and text, selected reference snapshot IDs, parent run ID, and requested tool capabilities. The app never writes credential values to `workspace.db` or the run log. Directory handles are live supervisor resources, not durable database values; restart requires new identity checks and a new attempt.
2. Preflight the current folder identity, account profile, required tool permissions, convention payload, and execution environment. A non-VCS mutating run additionally requires enablement for that exact project/folder identity; rebind clears it. Working directory alone does not confine provider file access, so the preview states the mode's actual scope and requires explicit run approval if it can write outside the target. An account label is not identity proof. Provider-specific profile isolation must pass a real credential-isolation smoke test before the UI claims concurrent accounts for that mode. Unavailable or unverified modes remain explicit rather than silently switching to another account or billing method.
3. Spawn the CLI with an argument array and a per-run environment. For every mutating run, hold identity-checked handles for the locked host root and selected working directory through run cleanup and evidence capture. Immediately before spawn, re-resolve the configured paths and fail preflight if their current identities differ from the held handles or the Git/jj working directory escapes its worktree. Set the child's actual working directory from its held handle, or use an equivalently proven identity-bound mechanism; do not resolve a symlink for locking and then spawn from its original pathname. A later symlink retarget cannot redirect that child, although a transient change that returns is not claimed detectable. Ordinary-folder inventories use the held root; Git/jj worktree review/diff materialization follows the separate [Review identity contract](architecture.md#review-worktree-identity-boundary), because the current Review API is path-based. A Docker mode additionally proves each host bind source matches its locked identity at container creation and accounts for every writable host mount before it can be enabled. Capture stdout and stderr as bounded streams and parse documented events. Persist only allowlisted event metadata and terminal fields; any tool input/output or model text must pass credential redaction and the separate content-artifact policy before persistence. If that check cannot classify content, keep it transient and record only a redacted summary and hash. The app must not infer success from process exit code alone: [Antigravity headless permissions can soft-deny tools and still exit `0`](https://www.antigravity.google/docs/cli/headless/).
4. Record a provider session/conversation ID when it arrives. Show queue, preflight, running, waiting for input, succeeded, failed, cancelled, and interrupted as separate states. A missing terminal event, parse failure, or process crash is not success. Provider internals are not independently managed subagents unless the adapter exposes verifiable child lifecycle data; app-owned subagents are child runs with their own snapshots.
5. Cancellation targets only the owned provider process tree and execution resources. Give the provider a documented graceful signal or command when available, then bounded TERM and precise KILL if needed, and record the terminal event, process exit, cleanup, and any observed target changes separately. A restart without a verified live process marks the attempt interrupted; resume is an explicit new attempt only after the provider's behavior has been tested.

Provider permission controls differ: [Claude Code](https://code.claude.com/docs/en/cli-reference) exposes permission mode and tool allow/deny flags, [Codex](https://learn.chatgpt.com/docs/developer-commands?surface=cli) exposes sandbox and approval controls, and [Antigravity](https://www.antigravity.google/docs/cli/headless/) has headless permission rules. The UI should describe the chosen provider's effective capability set, not display one generic switch that implies equivalent guarantees. Antigravity documents `SUCCESS`, `ERROR`, `CANCELED`, `INTERRUPTED`, `INVALID`, `WAITING`, and `RUNNING` result statuses. Only `SUCCESS` with no unmet required-tool operation can map to app success; `INVALID` is a failure and `RUNNING` is incomplete even if a result envelope was emitted. The other statuses retain distinct app states.

## Convention delivery and visibility

When a project has an applied version, the app renders one clearly labeled **Project conventions** section into that run's prompt, alongside separately labeled task instructions and quoted reference material. With no applied version, the preview and run snapshot record a null convention version and an empty convention payload; no placeholder rule is sent. The app records the exact outgoing text, ordering, hash, CLI flags, checkout, and delivery path. This route does not create or overwrite native instruction files in the checkout. It also leaves each provider's normal discovery enabled. Claude's documented [`--append-system-prompt`](https://code.claude.com/docs/en/cli-reference) is a possible provider-specific higher-authority mode, but it has different precedence and resume behavior; the common contract does not silently select it. A provider conversation may resume only with the same convention snapshot and digest. If the active version changed, the app starts a fresh provider conversation, or lets the person explicitly continue the old snapshot with a warning; it never claims that a newly sent version replaced prior conversation instructions.

Native instructions still matter. [Claude Code](https://code.claude.com/docs/en/memory) can load managed, user, project, imported, and local `CLAUDE.md`/rule content; [Codex](https://developers.openai.com/codex/guides/agents-md) discovers global and path-specific `AGENTS.override.md` or `AGENTS.md`; [Antigravity](https://www.antigravity.google/docs/rules/) combines workspace, directory, global, and plugin rules with trigger and size limits. Their order and authority are not equivalent. The app can show its outgoing payload and the native file inventory it was able to inspect, but cannot claim to know the complete model context from that alone. Missing visibility, conflicts, truncation risk, and provider-specific loading evidence appear beside the pre-run preview and saved run snapshot.

Claude documents an `InstructionsLoaded` hook and `/context` inspection in its [memory guide](https://code.claude.com/docs/en/memory), which can strengthen the observed native-file list. No comparable complete, machine-verifiable context attestation is established for Codex or Antigravity here. A provider's answer about what it read is diagnostic evidence, not proof that the full native context was delivered. Reusing a Claude session also matters: its [system-prompt flags are recorded on the first request and may not change on resume until compaction](https://code.claude.com/docs/en/cli-reference). The per-run user-prompt section avoids treating a changed system-prompt flag as immediately applied on a resumed session.

## First real adapter proof

Use a disposable checkout with harmless instructions and normal native discovery. For each provider, verify a noninteractive run from the intended working directory, the exact app convention section delivered once, parsed live and terminal events, provider session ID persistence, permission-denial reporting, cancellation/cleanup, and explicit resume as a new attempt. A Git/jj proof must reject a checkout or subfolder binding that is already rebound at the final dispatch check; if a symlink changes afterward, the child must still run in the held worktree and never edit the new target. The separate Review proof retargets the registered checkout before worktree evidence materialization and reports unavailable/unverified evidence rather than another checkout's diff. For each provider mode that claims ordinary-folder support, also edit a disposable non-VCS folder after enablement, show effective permissions and an in-root changed-path report, reject a binding already rebound at dispatch, and prove a later alias retarget cannot redirect the child or evade overlapping host-directory locks. A symlink target write and an out-of-root write must show the report's limits instead of a false **no changes**. If Docker support is claimed, prove bind identity and each writable host mount's boundary. Compare the saved preview with the actual outgoing bytes. Apply a new convention version between attempts and prove that resume retains the old snapshot or starts a fresh provider conversation, never displaying mixed context as the new version alone. Check native-file visibility separately and label any unverified provider loading. For every account mode claimed as concurrent, authenticate two accounts of the same provider in distinct app-owned profiles and run them simultaneously on separate checkouts without either run changing the other's credential state. Do not present numerical plan concurrency as proven by an adapter test.

The selected first actual Codex/Claude mode uses one existing local profile per provider and carries no concurrent account-isolation claim. The broader proof requires actual authenticated use and provider entitlements; a read-only connection-test slice or help/documentation review cannot establish mutating execution or every mode listed here. Any future concurrent account mode must prove credential isolation before the app offers it.
