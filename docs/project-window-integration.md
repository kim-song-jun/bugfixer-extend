# Editable project-window integration contract

Status: proposed implementation design for the user's selected **one native window per project**, with dashboard, editable files, and Whiteboard reviews in Code OSS editor tabs. It is source-backed design material, not implemented product behavior. The inspected Whiteboard source is pinned at [`4ecc5704cb19d1dc04304ae6956200227d483e27`](upstream-base.md#pinned-source-and-notices).

## Three explicit window modes

The current renderer entry chooses `navigator.desktop.main` for *any* workspace and `review.desktop.main` for an empty window ([entry selection](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/code/electron-browser/workbench/workbench.ts#L398-L414)). That test cannot distinguish an editable project folder from the generated Review source navigator. Add a trusted launch-mode discriminator for these three product-owned modes:

| Mode | Workspace and first surface | Ownership |
| --- | --- | --- |
| Review Home | No project folder; existing Review shell and Home canvas | Whiteboard Review profile |
| Review source navigator | Generated workspace for pinned historical sources; preserve its `files.readonlyInclude: {"**/*": true}` default | Review service ([source](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/review-api/local-data.ts#L388-L420)) |
| Editable project | App-owned project workspace pointing to the real folder; dashboard editor tab first, ordinary file editing, Review canvas tabs when available | Workspace service and project UUID |

The main process selects the mode when it opens a window and binds the renderer's numeric window ID to the project UUID. A folder path or a renderer-provided project ID is not authority to change modes. A project-mode window must not inherit navigator read-only settings. The project entry composes stock editor/workspace contributions with the Review canvas services it needs; it does not import the entire Review Home behavior merely to gain a review editor. Whiteboard currently registers the Review canvas alongside Home opening and Review-specific shell services in [`review.common.main`](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/review.common.main.ts#L6-L57), so extracting a project-safe contribution boundary is a first implementation step.

## Durable identity and launch

`projectId` is the app-generated, stable project UUID; `windowId` is only the current native process's handle. Store a distinct app-owned Code OSS workspace descriptor per project under the app profile, with its actual project folder as a member. Its URI stays stable when the folder path is rebound, and it is intended to separate editor-restoration identity even if two project records point to the same folder. The descriptor is not a project file and contains no credentials or navigator read-only override. Project state in `workspace.db` records the folder/checkout binding, active task ID, dashboard position, and whether its window was open at quit. The app owns the project-to-workspace association and window restoration list; a packaged restart test must prove Code OSS actually isolates editor groups by those workspace URIs.

Opening a project follows one path in the app main process:

1. Resolve `projectId` and its folder binding from `workspace.db`. A missing folder leaves that project's window on a **Rebind folder** state; it never substitutes another path.
2. If the registry already has a live window for this project, focus that window. Otherwise the **main process** opens its app-owned workspace descriptor with an explicit project launch mode and `forceNewWindow:true`. `IWindowsMainService.open` returns `ICodeWindow[]` ([interface](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/platform/windows/electron-main/windows.ts#L25-L40), [implementation](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/platform/windows/electron-main/windowsMainService.ts#L294-L307)); bind the resulting window ID to `projectId` before accepting its project commands, then wait for its ready signal. The renderer-facing native host `openWindow` returns only `Promise<void>` and cannot provide this ID ([source](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/workbench/services/host/electron-browser/nativeHostService.ts#L118-L140)). The implementation must verify that window settings do not override `forceNewWindow`.
3. Project commands carry a `projectId`; the main process checks the sender window ID against the registry and task ownership before handling a task, file, or review command. Closing removes the ephemeral registry entry and saves the project view state. Relaunch restores only the projects recorded as open at quit.

The launch-mode field, workspace-descriptor lifecycle, and registry-to-window handoff need a packaged-fork proof. They are proposed integration seams, not claims that Whiteboard already exposes a project API.

## Dashboard, file, and review editor identities

Give the dashboard its own serializable native editor input keyed by `projectId`; it is not Whiteboard's `home` target. Restore or create exactly one dashboard tab in that project's workbench and keep it first in the tab strip. Restored file and review tabs remain after it, and startup does not steal focus from a restored active editor. A task's selected ID lives in workspace state independently of the file or review URI; opening one file from two tasks changes explicit task context instead of assigning two task owners to one file tab. New dashboard UI follows the required FSD `app → pages → widgets → features → entities → shared` direction with slice public APIs; the Code OSS editor input and IPC adapters are platform glue around it.

Whiteboard's existing Home input is singleton and cannot close or move to a separate window ([input](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/browser/parts/canvas/reviewCanvasEditorInput.ts#L76-L91)); the tab service makes it sticky when opened ([service](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/services/reviewCanvasEditorTabsService.ts#L70-L73)). Its contribution opens Home after editor restoration and also reopens Home when a non-API canvas closes ([contribution](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/browser/parts/canvas/reviewCanvasEditor.contribution.ts#L61-L92)). Both Home side effects must stay in Review Home mode; project mode initializes Review canvas and catalog access without inserting a second Home tab.

The Review tab service already keys an API review as `api:<reviewId>` and opens it in an existing or active editor group ([tab service](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/services/reviewCanvasEditorTabsService.ts#L76-L98), [group reuse](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/services/reviewCanvasEditorTabsService.ts#L201-L207)). Its serializer persists API targets through native editor restoration ([serializer](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/browser/parts/canvas/reviewApiEditorSerializer.ts#L7-L36)). The app opens a task's stored `reviewId` through **that project's** workbench tab service after main-process ownership checks; repeated opens reveal the same input. A missing/deleted review remains an unavailable task link with a repair action.

## Review API and external-open routing

The task-review write sequence remains the [durable `commandId` contract](architecture.md#review-link-write-contract): register the current Git/jj worktree, persist an outgoing create command in `workspace.db`, call Review API create with `open:false`, save the returned `reviewId`, and open its tab in the owning project window. `open:false` prevents Whiteboard's create path from auto-opening the review in its attached Desktop ([create path](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/review-api/http.ts#L1246-L1264)). The first runtime proof must confirm that opening the canvas directly after create loads everything needed without the API's separate asynchronous pinned-workspace preparation; if preparation is required, make it a server operation independent of choosing a window.

The current HTTP `/:id/open` path passes only `reviewId` and title to the desktop verb ([API path](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/review-api/http.ts#L502-L559)). The server relay accepts only **one** attached writer ([relay](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/server/global-verb-relay.ts#L33-L62)); it has no project-window selector. Today each canvas tries to attach a control stream as it mounts ([canvas part](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/browser/parts/canvas/reviewCanvasPart.ts#L277-L292)), and the server rejects a second attachment with HTTP 409 ([control route](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/server/desktop-server.ts#L605-L627)).

Move that single control-stream attachment and its reconnect/abort lifecycle into one main-process dispatcher; Review Home and project canvases must not independently compete for it. The existing renderer service starts its own persistent `/control` reconnect loop ([connection service](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/services/reviewDesktopConnectionService.ts#L423-L455)); disabling only the canvas callback would leave a competing connection. The dispatcher owns exactly one stream, forwards typed verbs to the selected renderer, and returns the renderer result to the server. Closing one project window cancels its pending dispatches without ending the app-wide stream; Review server shutdown or app quit aborts the stream and drains pending calls.

In-app task opens route through the app's project-window registry directly, not through the global HTTP open route. For an external `/:id/open`, the dispatcher resolves `reviewId` against task/project links. A unique owner opens or focuses that window, waits for readiness, and returns success only after its `api:<reviewId>` tab opens; the response includes that window's actual `softwareMapEnabled` setting, as the current Review callback requires ([server callback](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/src/server/desktop-server.ts#L224-L255)). Multiple owners or no link trigger an explicit destination chooser, including Review Home for an unlinked review. Selection is one-time unless the user separately saves a task link; repository path alone cannot select among task owners. The chooser and window-open operation have a combined deadline below the relay's 45-second timeout. Cancellation, timeout, a closed destination, or no viable destination returns a visible 409 open error with retry guidance; no tab is reported opened and no late callback may open one after the error. The next open request can be retried. No last-focused-window fallback chooses a task-linked review.

`authoringCapabilities` is served from an app/profile-level configuration provider and must report the same `softwareMapEnabled` value as a Review Home canvas; a selected project window supplies that value for its own open result. `focusWindow` is a global app-focus action and may focus the last active valid app window. Other global Review verbs continue to target Review Home or return a visible unavailable result if their required surface is closed. Their existing request/response schemas and timeout behavior remain covered by compatibility tests.

The current canvas receives `serverUrl` and the Review token in its runtime config ([canvas bridge](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/browser/parts/canvas/reviewCanvasPart.ts#L413-L422)), and the Review app uses them for direct HTTP requests ([client](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/packages/review/app/src/host/review-client.ts#L4-L37)). That conflicts with the selected [main-process credential boundary](architecture.md#selected-data-boundary-app-owned-workspace-database). The desktop path must replace direct renderer HTTP with a host-provided typed Review gateway: main owns the URL/token, validates sender window, project/review binding, method and endpoint, and returns bounded results or cancellable streams through IPC. This migration includes every native `getConnection()` consumer: canvas, catalog, source, language features, structural diff, review tabs, and sharing; the desktop renderer API that returns the token is removed. Neither Home nor project renderer receives the token or an arbitrary-URL fetch capability. The separately hosted web Review client keeps its explicit HTTP transport; desktop chooses the gateway transport with no silent fallback to direct HTTP. A packaged test must inspect both renderer configuration and network requests for token exposure while exercising catalog, canvas edits, and live review updates.

The existing `openApiSource` action intentionally opens a separate navigator workspace with `forceNewWindow:true` ([source action](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/services/reviewCanvasEditorTabsService.ts#L104-L115)). Keep that path distinct; its pinned historical files remain read-only while editable project files use the real project folder.

## First-slice proof and sequencing

1. Import the pinned Whiteboard source with its dependent workspace packages and notices, then build and launch its unmodified Review desktop from the committed tree. The [source boundary inventory](upstream-base.md#buildable-source-boundary) lists what must travel together. This proof precedes editing the fork.
2. Establish explicit window mode and project workspace identity; launch two projects, including two records temporarily bound to the same checkout, without sharing a native window or restored tab state. Preserve separate Review Home and read-only navigator modes.
3. Add the project dashboard editor and app-owned workspace service. Create a task, edit/save a real checkout file, switch projects, close/restart, and confirm each window restores its dashboard, file tabs, and active task without cross-project attribution.
4. Register the checkout with Review API, create a task review with a durable command, and open it in the owning project's native tab. Simulate a lost create response and repeated opens; the task and tab keep one returned `reviewId`. Confirm direct canvas load after `open:false`, external-open routing with two project windows, chooser success/cancel/timeout, and exactly one healthy control-stream attachment rather than a 409 loop. Exercise catalog, edit, and watch through the token-owning main gateway; inspect renderer configuration and traffic for secret leakage.
5. In a disposable profile, use SQLite-aware backup operations for both `workspace.db` and `review-api.db`, restore them, and verify task/review links and an explicitly unavailable review. A copy of only a live main DB file does not prove recovery while WAL is active.
6. Inspect normal and narrow native windows before/after implementation, including tab order, text wrap, focus, scroll end, light/dark contrast, and actual editing. Run the selected UI verification path in [ux-flow.md](ux-flow.md#validation-when-implemented). A source-only or local TypeScript check does not prove the product window works.

The dashboard's detailed placement, provider account behavior, Docker boundary, and Notion authorization still have separate pending user choices. This contract fixes the already selected window and review behavior without deciding those unrelated questions.
