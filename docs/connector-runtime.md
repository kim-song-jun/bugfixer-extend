# Installable connector execution boundary

Status: the user selected **A — declarative installed packages** for the first public connector release, and source implements local installation of signed declarative packages. The user also selected first-party Slack, Notion, and public website URL import, plus signed-in selected-text capture through Ego. Public website URL preview/import is implemented in source with focused tests. Source implementation does not establish real Slack/Notion account behavior or packaged connector/Ego security proof; release gates below remain. The shared snapshot and consent contract lives in [architecture.md](architecture.md#imported-reference-and-connector-contract). The first project/task/review slice does not depend on this format.

## Existing desktop boundary

Whiteboard's Review profile starts a curated Code OSS extension host ([source](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/src/vs/review/editor.desktop.main.ts#L33)), but its [product configuration](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/code-oss/product.json#L182) has no general extension gallery. An installed reference connector does not need to be a VS Code extension or gain editor/terminal APIs. Keep its package registry, trusted interpreter, permission display, and snapshot writes app-owned. This leaves the current curated editor extensions available without treating their host as a permission boundary for user-installed code.

Review leaves its Code OSS chat/browser agent path inert. Its [upstream notes](https://github.com/devdotfast/whiteboard/blob/4ecc5704cb19d1dc04304ae6956200227d483e27/apps/review-desktop/UPSTREAM#L76-L104) explicitly defer three agent network-filter fixes because that path is inactive. The selected connector interpreter must not depend on this inactive filter. If the product later enables Code OSS agent network paths, resync and verify those fixes before enabling them; a separate connector broker does not cure an unrelated agent-host path.

The [VS Code extension host guide](https://code.visualstudio.com/api/advanced-topics/extension-host) describes local Node.js and browser-worker extension hosts. It does not document per-extension filesystem, network, or credential isolation. An executable package loaded into an ordinary Node extension host would therefore not satisfy a future installed-code permission contract; the selected declarative format runs no package code there.

## Enforcement facts

- The exact Node 24.18.0 runtime pinned by the Code OSS fork has a [Permission Model](https://nodejs.org/download/release/v24.18.0/docs/api/permissions.html), but Node says it is not a defense against malicious code. Its documented restrictions cover `node:fs`, process and worker creation, addons, WASI, and the inspector; its filesystem check does not cover every access path, including `node:sqlite`. It does not provide a documented per-domain network gate. It can reduce mistakes in trusted code, but cannot establish the installed-connector sandbox.
- Electron's [sandboxed renderer](https://www.electronjs.org/docs/latest/tutorial/sandbox) has no Node runtime and must delegate privileged filesystem and process actions to main through IPC. Its preload remains more privileged than page code. [Electron's security guide](https://www.electronjs.org/docs/latest/tutorial/security) requires context isolation, constrained IPC, restrictive CSP, permission handling, navigation/window limits, and avoidance of `file://` for untrusted content. A sandboxed renderer is a credible boundary against direct Node/filesystem access; it does not by itself mean that browser-mediated network requests are impossible. The main process must block those requests and expose only an allowlisted network broker.
- Apple's [XPC service guidance](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html) supports privilege separation with a separately sandboxed service. A helper without network entitlement plus a trusted network broker can give a stronger OS-level direct-network denial on macOS. This requires a signed helper target and a separately verified Windows runtime; [Windows AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) is a possible later boundary, not an already validated x86 port.

## Decision candidates

| Choice | Package and execution | What the user gains | Cost and boundary |
| --- | --- | --- | --- |
| **A — Declarative connector package (selected for the first public connector release)** | Manifest, endpoints, response mapping, and assets interpreted only by trusted app code; package data is never evaluated as code | Straightforward install and review for REST-like sources; no installed executable code | Complex source-specific logic and authentication must be added to the app or cannot be expressed; the format is intentionally limited |
| **B — Browser-target JavaScript in an Electron sandboxed renderer (feasibility study)** | App validates and loads each installed package into a dedicated sandboxed renderer and session; host brokers fetch, credentials, and snapshot writes | Flexible community connectors with a cross-platform JavaScript target while retaining one app-owned reference model | No Node modules or native addons in connector code; CSP and `webRequest` do not establish a complete direct-network denial because WebRTC is a separate transport; a renderer compromise remains outside this boundary |
| **C — Separately sandboxed native helper** | A bundled macOS XPC service runs a connector interpreter without direct network/filesystem entitlements; host broker delivers package bytes and mediates capabilities | Stronger OS-level separation for installed logic on macOS | XPC services are signed private targets bundled with the app, not user-installable plug-ins themselves; the interpreter, package transfer, signing, IPC, and crash lifecycle need design; later Windows needs an independently validated AppContainer or equivalent implementation |

The user selected **A** for the first public release. It satisfies installation without running third-party code, but it cannot support arbitrary connector logic or authentication flows. **B** remains a research option: [CSP `connect-src`](https://www.w3.org/TR/CSP3/#directive-connect-src) and Electron [`webRequest`](https://www.electronjs.org/docs/latest/api/web-request) can restrict ordinary browser request paths, but neither documents a complete WebRTC transport denial. Electron's [`disable_non_proxied_udp` policy](https://www.electronjs.org/docs/latest/api/web-contents#setwebrtciphandlingpolicypolicy) still permits some TCP WebRTC paths. B cannot meet a hard no-direct-network contract until a packaged-fork proof establishes an additional effective process-level denial or verified removal of uncovered transports. If arbitrary installed logic and OS-enforced direct-network denial are required on macOS in a later release, **C** is the stronger candidate; its Windows counterpart needs separate design and validation. Neither executable runtime is approved for the first release.

## Selected A contract and release proof

Source implements local installation for signed declarative packages. An installed package is data with a versioned, bounded schema for source metadata, permitted HTTPS hosts, endpoint templates, request parameters, response-field mapping, and supported host-owned authentication modes. The app validates every field and path before installation, rejects executable expressions and unknown capabilities, and interprets the package only in trusted code. The broker checks declared hosts, URL resolution, redirects, and account scopes on every request; it owns credentials and writes immutable snapshots. A connector that needs custom code or an unsupported authentication flow is reported as unsupported rather than silently given a broader runtime. The [candidate package format](declarative-connector-format.md) describes the contract; packaged security/release proof and a real account-backed connector import remain unverified.

The first installed test connector must import through the same discover/preview/import/refresh model as the first-party connectors, preserve original and refreshed snapshot versions, and fail to fetch an undeclared host or account. A malformed or executable field must be rejected at installation. Revoking the connection stops refresh while existing task evidence remains available. These are release gates for A; they do not claim arbitrary community connector compatibility.

## Conditional B feasibility proof

If B is selected for further research, an installed package targets browser JavaScript and declares an API version plus the exact network hosts, account scopes, local/browser capabilities, and source types it needs. The install and connection screens show these before use. The app copies the package to an app-owned location after validating its manifest, file paths, size, and content hashes; it serves only that package's approved assets through a constrained custom protocol registered on its dedicated session, without CSP-bypass or service-worker privileges. Each connector needs its own origin and session. The connector page must use `sandbox: true`, `nodeIntegration: false`, and `contextIsolation: true`, a restrictive response-header CSP, denied navigation/new windows/webviews, and both Electron permission check and request handlers set to deny unless explicitly granted. Worker and service-worker creation must be disabled. Neither provider tokens nor database paths are given to page code.

The trusted host validates sender identity and message schemas for a narrow API: discover, preview, fetch through the broker, import, and refresh. The broker checks the installed connector's granted hosts and account scopes on every request, including redirects. The dedicated session alone is not a deny rule: the host must own one `webRequest.onBeforeRequest` listener that rejects direct page network requests before loading connector code, and integration must prove no later listener replaces it. [Electron uses only the last listener for an event](https://www.electronjs.org/docs/latest/api/web-request). Navigation, frame navigation, redirects, and new windows require separate host-owned checks. WebRTC is a separate direct-network risk; its [documented policy](https://www.electronjs.org/docs/latest/api/web-contents#setwebrtciphandlingpolicypolicy) is not a complete disable switch. The design must find and verify a full direct-network denial, not infer it from CSP or the web request listener. The host attaches credentials only to a permitted broker request and writes immutable snapshots through the workspace service. Source content returned to an agent remains labeled reference data unless a person explicitly promotes text to an instruction under the [reference contract](architecture.md#imported-reference-and-connector-contract). CSP and the Electron sandbox are distinct layers; neither replaces the broker's checks.

The first installed test connector must fail closed when it attempts direct `fetch`, image/form/navigation/WebSocket egress, WebRTC/data-channel egress, worker/service-worker egress, local file/database access, an unauthorized IPC method, a denied host (including a redirect), or an undeclared account. A packaged-fork network trace must show that these attempts send no connector-origin direct packets; a listener replacement and custom-protocol registration check must confirm the deny rule remains active. For WebRTC, a single trace without observed traffic is insufficient: the API/transport must be disabled or an OS/process policy must be shown to deny the attempt. A legitimate declared broker request must import a snapshot with source/version metadata and survive refresh as an additional immutable version. Installation, revocation, cancellation, crash, and app restart must leave no live connector process or credential leak. The denial tests and a packaged macOS run are release gates for B; until they pass, B cannot be shipped as a runnable installed-code format.
